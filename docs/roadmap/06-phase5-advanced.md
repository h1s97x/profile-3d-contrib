## 一、定位

本阶段收纳**不阻塞任何前序阶段**的探索性能力。它们的共同特征是:有真实用户诉求,但尚未验证规模,或引入显著的新维护成本。

因此本阶段文档的定位是**可行性评估**,而非实施计划。每一项须走 RFC 流程,由社区反馈决定是否进入实施。

> **本阶段不承诺具体时间。** 任何一项进入实施时,都需要单独补充本文件缺失的「工期 / commit 切分 / 验收标准」。

## 三、逐项评估

### A1 `--dry-run`

**诉求**:用户在改 settings JSON 时,想先确认会生成哪些文件,而不必真的跑一遍(尤其是本地调试多主题组合时)。

**现状基础**:阶段 3 的 `ResolvedConfig` 已含 `dryRun: boolean`,CLI 也已解析 `--dry-run`。**本项主要是接上打印逻辑**。

**可行性**:**高**。工作量 < 1 天。

设计要点:

- 输出形如 `Would write: profile-3d-contrib/profile-green.svg (48 KB)` 的清单
- **仍然完整执行数据拉取与渲染**,只是不落盘 —— 因为用户真正想验证的是渲染是否成功,而不只是文件名。若跳过渲染,「dry-run 能跑通」就失去了意义
- 退出码 0(这是预期行为,不是错误)
- 需同时提示:若配置了 `SETTING_JSON`,还要列出校验结果

**风险**:极低。

---

### A2 API 结果缓存

**诉求**:本地调试主题时,每次都重新请求 GitHub API,既慢又消耗限流配额。

**可行性**:中。

设计要点:

- 缓存键:`sha256(endpoint + username + year + maxRepos)`,不含 token
- 缓存内容:`UserInfo` 的 JSON 序列化结果,**不含任何仓库名**(仓库名已在 `UserInfo` 中被聚合掉,需在实现时逐一确认)
- 存储位置:`$XDG_CACHE_HOME/profile-3d-contrib/` 或 `.cache/`(**不写入输出目录**,避免污染用户的 git 仓库)
- TTL:默认 1 小时,`--no-cache` / `--refresh-cache` 可覆盖
- 失效策略:内容哈希比对,内容未变则跳过写文件(与阶段 4 的幂等写入协同)

**风险**:

| 风险 | 等级 | 说明 |
|---|---|---|
| **token 泄露到磁盘** | **高** | 缓存文件若含 token 即为严重漏洞。缓解:缓存内容仅限 `UserInfo`,并在代码中加显式断言禁止写入 token 字段;加一条测试断言缓存文件**不含** token 字符串 |
| 私有仓库信息落盘 | 中 | `UserInfo` 中不含仓库名,但需确认 `contributesLanguage` 的语言名不构成敏感信息。缓解:提供 `--cache-dir` 显式指定,默认目录加权限 `0700` |
| 缓存陈旧导致数据错误 | 中 | 缓解:TTL 短 + `--refresh-cache` + 日志明确标注「using cached data from HH:mm:ss」 |
| CI 环境缓存语义混乱 | 中 | GitHub Actions 中默认**禁用**缓存(除非显式开启),避免与其他 action 抢占 `~/.cache` |

**结论**:可行,但**必须**先完成 token 泄露的防护设计与测试,再考虑开放给用户。

### A3 PNG 导出

**诉求**:部分平台(如某些 IM、Notion)不渲染 SVG,需要位图。

**可行性**:中,且**代价被低估**。

| 方案 | 体积影响 | 平台兼容性 | 备注 |
|---|---|---|---|
| `sharp`(libvips) | +~30 MB 含原生二进制 | 最好 | GitHub 的 ubuntu-latest runner 支持预编译二进制;但 `dist/` 会暴涨,且需处理多平台(项目支持在 macOS / Windows 本地运行) |
| `@resvg/resvg-js` | +~8 MB | 好 | Rust 实现,预编译二进制,体积更可控 |
| `resvg` WASM | +~5 MB,无原生 | 中 | 纯 JS,跨平台最简单,但性能较慢 |
| 外部 CLI(`rsvg-convert`) | 0 | 差 | 需用户在 runner 上自行安装,违背 Action 开箱即用原则 |

**关键矛盾**:PNG 导出会显著增加 `dist/` 体积,与[阶段 4](./05-phase4-perf-ux.md) 刚达成的瘦身目标**直接冲突**。

**建议方案**:

- PNG 导出**不作为默认能力**,而是**可选开关**(`--format png`),且依赖以**可选依赖**方式声明
- 或**独立发布**一个 `@h1s97x/github-profile-3d-contrib-png` 包,主包保持轻量

**结论**:倾向第二种。**若走第一种,需在阶段 4 完成后重新评估体积预算**。

### A4 多用户聚合

**诉求**:在组织场景下,一页展示整个 team 的贡献情况。

**可行性**:**低**。这是本阶段唯一需要**扩展领域模型**的能力。

现有 `UserInfo` 是**单用户**结构:

```typescript
// src/type.ts(现状)
export interface UserInfo {
    readonly isHalloween: boolean;
    readonly contributionCalendar: Array<CalendarInfo>;
    readonly contributesLanguage: Array<LangInfo>;
    readonly totalContributions: number;
    // ... 全部为标量或单用户数组
}
```

多用户需要决定:

| 问题 | 选项 | 复杂度 |
|---|---|---|
| 日历如何合并 | 逐格求和 / 平均 / 仅总量 | 中 |
| 语言如何合并 | 全局聚合 / 分用户堆叠 | 中 |
| 雷达图如何表达 | 每人一个多边形?/ 均值单多边形? | **高**(语义问题) |
| API 成本 | N 个用户 × (1 + 分页)次查询 | 需严格限流,极易触发 secondary rate limit |
| 布局 | N 个日历如何排布 | **高**(现有布局是硬编码的 1280×850) |

**风险**:API 限流。GitHub 的 secondary rate limit 对并发查询非常敏感,批量拉取 20 个用户很可能直接被限流。

**结论**:**建议不做**,或大幅缩小范围为「仅汇总总量指标」而非完整可视化。若社区确有强需求,应先在 issue 中收集用例,再决定。

---

### A5 自定义布局预设

**诉求**:提供若干预设(如「紧凑」「宽屏」「无透视」),用户不必手填 `LayoutOptions`。

**可行性**:高。阶段 4 的 `LayoutOptions` 已把参数抽成对象,预设只是若干常量组合。

```typescript
// src/renderers/presets.ts(计划内容)
export const LAYOUT_PRESETS = {
    default: DEFAULT_LAYOUT_OPTIONS,
    compact: { ...DEFAULT_LAYOUT_OPTIONS, columnDivisor: 74, barHeightScale: 110 },
    wide: { ...DEFAULT_LAYOUT_OPTIONS, canvasWidth: 1600 },
    flat: { ...DEFAULT_LAYOUT_OPTIONS, angle: 0 },
} as const;
```

**风险**:低。**但收益也有限** —— 用户通过 `schema/settings.schema.json` 的补全已经能方便地调整这些值。列为 P3。

---

### A6 输出为 GitHub Pages 站点

**诉求**:一次生成多个主题并输出为可直接发布的小站点(index.html + 图片)。

**现状关联**:`EXAMPLES.md` 的进阶示例已展示用 `crazy-max/ghaction-github-pages` 把 `profile-3d-contrib/` 推到独立分支。说明用户已在**手工拼装**这个流程。

**可行性**:中。

设计要点:

- 生成 `index.html`,含全部 SVG 的 `<picture>` 引用与 `prefers-color-scheme` 切换
- **需要 11 份语言的 l10n 整合**(阶段 4 产出)
- 若同时实现 A3,此处即 PNG 的天然落点

**风险**:中。生成 HTML 意味着引入模板与转义逻辑,需注意 XSS(用户名、l10n 文案都需转义)。

**结论**:可行,是 A3 的良好载体,建议与 A3 绑定评估。

## 五、建议优先级

若资源允许,推荐顺序:

1. **A1 `--dry-run`** —— 成本极低,阶段 3 已备好接口,可立即交付
2. **A5 布局预设** —— 成本低,与阶段 4 无冲突
3. **A6 + A3 站点与 PNG** —— 绑定评估,PNG 走独立包以避免体积冲突
4. **A2 缓存** —— 仅在本地调试痛点被反复反馈后推进
5. **A4 多用户聚合** —— **建议不做**,除非有强需求

## 六、风险

| 风险 | 等级 | 说明 |
|---|---|---|
| PNG 依赖破坏阶段 4 体积成果 | **高** | 必须走独立包或可选依赖 |
| 缓存泄露 token | **高** | 见 A2,须显式断言 + 测试 |
| 能力发散导致维护成本上升 | 中 | 本项目由单人维护,阶段 5 的每一项都应是「被明确要求」而非「顺手做」 |
| 多用户 API 限流 | 中 | A4 若实施需严格串行 + 缓存 |
| 11 份文档同步成本累积 | 低 | 每个新特性都需同步 11 份 README,是持续放大的负担 |

## 七、出口条件

本阶段**无统一出口条件**。每一项独立走 RFC 流程、独立排期、独立验收。
